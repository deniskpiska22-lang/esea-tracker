# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

ESEA Tracker — a community site for tracking FACEIT ESEA CS2 tournaments, teams, matches, players and ratings. React 19 + Vite SPA frontend, Supabase (Postgres + Auth) as the backend, Vercel for hosting the frontend and serverless API, Railway for long-running background workers.

## Commands

```bash
npm run dev       # Vite dev server
npm run build     # production build
npm run lint      # eslint .
npm run preview   # preview a production build
```

There is no test suite/framework configured in this repo.

### Data sync scripts

Most scripts that touch Supabase or FACEIT need secrets and are run with `node --env-file=.env.local scripts/<name>.js` (see the corresponding `npm run` script for the exact invocation) — never add the `VITE_` prefix to `FACEIT_API_KEY` / `SUPABASE_SECRET_KEY` (a.k.a. `SUPABASE_SERVICE_ROLE_KEY`), since that prefix exposes a var to the client bundle.

Two generations of the team/match discovery pipeline coexist:

- **v2 (current)** — standings-driven discovery, configured in `scripts/v2/standings.config.json`:
  ```bash
  npm run v2:discover-entities   # walk the FACEIT season tree, find all stage/conference groups for Entry/Intermediate/Main/Advanced
  npm run v2:sync                # pull standings for configured groups -> data/v2/standings-teams.json + src/data/teams.generated.js
  npm run v2:sync:profiles       # same, plus team profiles/rosters/player countries (needs FACEIT_API_KEY)
  npm run sync:full              # v2:sync + sync:auto
  ```
- **legacy match sync** — team-list driven, still running in production for match lifecycle + stats:
  ```bash
  npm run sync:auto              # scripts/autoSyncMatches.js: discover new matches, upsert to Supabase, update live scores
  npm run sync:live              # same, invoked by the sync-live GitHub Action every 5 min
  npm run refresh:matches        # updateUpcomingMatches -> updateMatches -> syncMatchesToSupabase
  ```

Ratings/stats maintenance (run ad hoc, not on a schedule):
`ratings:recalculate`, `ratings:init`, `sync:rosters`, `stats:backfill`, `stats:full`, `stats:normalize`, `rosters:backfill`.

## Architecture

### Data has two sources, by design

- **Bundled static data** in `src/data/*.js` / `*.json` (e.g. `teams.generated.js`, `matchStatsV3.json`, `playerAverageRatings.json`, `rankingSnapshot.json`) — generated by the sync scripts above and committed, so the site has content even without a live DB round-trip. `src/data/teams.js` is the single import surface for team data and just re-exports `teams.generated.js`; the old hand-maintained list is kept as `teams.legacy.js` for reference only.
- **Live Supabase queries** for anything that changes after build time (recent matches, head-to-head, per-team map stats, auth/profile data) — done either directly from the browser via `src/lib/supabaseClient.js` (anon/publishable key) or through `/api/*` serverless functions when the service-role key or `FACEIT_API_KEY` is needed server-side (`api/team-stats.js`, `api/match.js`, `api/home-matches.js`, `api/submit-team.js`, `api/veto.js`).

When changing how a page gets its data, check which of these two paths it's actually on — a component can look "static" while actually reading Supabase at runtime, or vice versa.

### FACEIT has two API surfaces in use

- Official Open Data API v4 (`open.faceit.com/data/v4/...`), needs `FACEIT_API_KEY`, used for per-match/player detail lookups.
- Undocumented internal endpoint (`www.faceit.com/api/team-leagues/v2/...`), used for season-tree/standings/discovery — this is what lets the pipeline find registered teams and scheduled matches without already knowing team IDs, and it rejects `MATCH_STATUS_READY`/`MATCH_STATUS_ONGOING` as filters (see `AUTOMATION.md`).

### Routing and app shell

All routes are declared in `src/main.jsx`, lazily imported per page (this was a deliberate change — see `51a9e82` — to keep the initial bundle small instead of one shipping the whole site). `src/App.jsx` is the layout shell (`Outlet`-based): nav, search, "submit a team" modal, auth menu. Cross-cutting state lives in `src/context/AuthContext.jsx` (Supabase session/profile) and `src/context/LanguageContext.jsx` (RU/EN via a `tr(ru, en)` helper used throughout).

### Background workers (Railway) vs scheduled jobs (GitHub Actions)

Three long-running Node processes are deployed as separate Railway services, each with its own `railway.*.json` pointing at a different entrypoint:

- `scripts/worker.js` (`railway.json`)
- `scripts/statsWorker.js` (`railway.stats-worker.json`)
- `scripts/tournamentWorker.js` (`railway.tournament-worker.json`)

Short, periodic jobs (match sync every 5 min, stat-job processing) instead run via `.github/workflows/*.yml` hitting the `npm run` scripts directly — no Railway service for those.

`nixpacks.toml` disables the `node_modules/.cache` mount (`NIXPACKS_NO_CACHE=1`) because `npm ci` deletes `node_modules` first, and Nixpacks' cache mount there causes an `EBUSY` error.

### Supabase

Schema lives in `supabase/migrations/*.sql`, applied in order. `supabase/functions/login-with-username` is the one Edge Function, used only to resolve a username to an email for login (email/password auth works without deploying it).
